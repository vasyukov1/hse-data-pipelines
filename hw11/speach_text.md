# Текст для защиты проекта CourseWork Data Quality Pipeline

Сегодня я представляю проект `CourseWork Data Quality Pipeline`, который я реализовал на `Argo Workflows`. Идея проекта в том, чтобы автоматизировать базовую проверку студенческих проектных работ или курсовых, которые сдаются в виде архива по URL.

На вход пайплайн получает ссылку на архив проекта, имя архива, название проекта, имя студента и список обязательных файлов или директорий. После этого pipeline последовательно выполняет четыре шага: скачивает архив, распаковывает его, проверяет структуру проекта и формирует итоговый markdown-отчёт.

С точки зрения архитектуры я не стал делать один большой workflow с жёстко зашитой логикой. Вместо этого я вынес основные операции в отдельные `WorkflowTemplate`. Это соответствует идее переиспользуемой оркестрации: каждый шаблон можно применять отдельно и повторно использовать в других сценариях.

Первый шаблон называется `download-artifact-template`. Он универсально решает задачу скачивания файла по URL. На вход он принимает `file-url` и `output-filename`, а на выход отдаёт `downloaded-file` как artifact. Это удобно, потому что следующий шаг не зависит от конкретного способа скачивания, а получает уже готовый артефакт.

Второй шаблон — `unpack-archive-template`. Он принимает архив как input artifact и параметр `archive-filename`, чтобы понять формат. Внутри шаблон распознаёт `.zip`, `.tar.gz` и `.tgz`, распаковывает архив в рабочую директорию и возвращает каталог проекта как artifact `unpacked-project`. Это уже более универсальный компонент, который можно использовать не только для курсовых, но и для любых задач распаковки артефактов перед обработкой.

Третий шаблон — `project-check-template`. Он принимает распакованный проект и строку `required-paths`, например `README.md,go.mod,cmd`. Шаблон проходит по каждому обязательному пути, проверяет его наличие и формирует три результата. Первый — параметр `check-status`, где будет `OK` или `FAILED`. Второй — параметр `missing-paths`, где перечислены отсутствующие файлы или каталоги. Третий — текстовый artifact `check-report`, в котором указаны дата проверки, список обязательных путей, итоговый статус и дерево проекта на глубине до трёх уровней. Важно, что этот шаг не падает даже при статусе `FAILED`, потому что задача пайплайна не аварийно остановиться, а всё равно собрать диагностический отчёт.

Четвёртый шаблон — `report-template`. Он получает имя проекта, имя студента, статус проверки, отсутствующие пути и промежуточный отчёт. На их основе он формирует итоговый markdown-файл `final-report`. В этом файле есть краткая сводка по проверке и детальная часть с содержимым `check-report`.

Основной `Workflow` собран в виде `DAG`. Это важно, потому что DAG наглядно показывает оркестрацию зависимостей между задачами. Последовательность такая: `download-project`, затем `unpack-project`, затем `check-project`, и в конце `generate-report`. Все связи между шаблонами сделаны через `templateRef`, а данные передаются через `outputs.artifacts` и `outputs.parameters`. Для удобства повторных запусков workflow создаётся через `generateName`, поэтому можно подряд показать успешный и ошибочный сценарии без конфликтов по имени.

Чтобы проект был воспроизводимым, я добавил локальный demo-контур. Он поднимается на `kind`, устанавливает `Argo Workflows` из официального quick-start манифеста и использует встроенный `MinIO`, поэтому все `outputs.artifacts` реально работают. Кроме того, я добавил отдельный demo-server внутри кластера, который раздаёт тестовые архивы с проектами. За счёт этого демонстрация не зависит от внешних URL и от ручной подготовки файлов.

Если показать пример запуска, то он выглядит так: сначала я выполняю `./hw11/scripts/bootstrap-local-demo.sh`, этим я поднимаю кластер, Argo, MinIO и demo-server. Затем применяются шаблоны, и после этого я запускаю успешный сценарий через `./hw11/scripts/run-demo-success.sh` или сценарий с ошибкой через `./hw11/scripts/run-demo-failure.sh`.

Дальше в интерфейсе Argo или через CLI можно посмотреть список запусков командой `argo list -n argo`, затем детали через `argo get -n argo <workflow-name>` и логи через `argo logs -n argo <workflow-name>`. На защите удобно открыть именно DAG и логи шага `check-project`, потому что там сразу видно, какие пути были проверены и какой статус получился. Также в логах шага `generate-report` печатается итоговый markdown-отчёт, поэтому можно сразу показать финальный результат.

Я бы показал два сценария. Первый — успешный, когда в архиве есть все обязательные элементы, и тогда статус `OK`. Второй — сценарий с ошибкой, например если нет каталога `cmd`. Тогда `check-status` будет `FAILED`, но workflow всё равно завершится корректно, потому что последний шаг соберёт финальный отчёт с указанием отсутствующих путей. Это важный момент: pipeline не просто валится на ошибке, а выдаёт полезный результат для анализа.

Итоговая ценность решения в том, что оно демонстрирует ключевые возможности Argo Workflows: переиспользуемые шаблоны, параметризацию через `inputs.parameters`, передачу файлов через `artifacts`, передачу метаданных через `parameters` и сборку целостного пайплайна через DAG. При этом сам проект остаётся понятным, компактным и пригодным для реального учебного использования.

Если кратко сформулировать итог, то я построил мини-проект для автоматической проверки структуры студенческих работ, в котором каждый шаг изолирован, переиспользуем и прозрачно оркестрируется через Argo. Такой подход можно дальше расширять: например, добавить проверку `Dockerfile`, `requirements.txt`, линтинг кода или загрузку отчёта в внешнее хранилище.
