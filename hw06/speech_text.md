## Вступление 

Сегодня я расскажу про домашнее задание по теме "DataFrame vs RDD в Apache Spark". Задание было такое: взять несколько кейсов обработки данных, реализовать их двумя способами – через DataFrame API и через RDD – и сравнить производительность. Плюс два дополнительных кейса, где SQL-запрос может выигрывать у DataFrame.

Спойлер: DataFrame оказался быстрее во всех трёх основных кейсах. Это можно объяснить конкретными оптимизациями, которые Spark применяет "под капотом".

Для начала – про архитектуру. В Spark есть два уровня API:
- **RDD (Resilient Distributed Dataset)** – низкоуровневый. Вы сами пишете, *как* обрабатывать данные: какую функцию применить, как группировать, как агрегировать.
- **DataFrame** – высокоуровневый, декларативный. Вы говорите *что* хотите получить, а Spark сам решает, *как* это сделать эффективнее всего.

Вот это "сам решает" – и есть главный источник преимущества. Этот "умный решатель" называется **Catalyst Optimizer**.

## Кейс A: Множественные агрегации

Первая задача классическая: посчитать несколько метрик по группам. У нас 5 миллионов строк, 1000 уникальных ключей, и нужно для каждого ключа найти сумму, среднее и минимум.

Вот как это выглядит на DataFrame:
```python
df.groupBy("key").agg(
    F.sum("value"),
    F.avg("value"),
    F.min("value")
)
```
Одна строка – три метрики.

А вот RDD-вариант – три отдельных вызова `reduceByKey`, по одному на каждую метрику. И вот тут начинается проблема.

**Результат:** DataFrame – 0.10 секунды, RDD – 12.16 секунды. Разница в 120 раз.

Почему? Чтобы понять, нужно посмотреть, что происходит физически на кластере.

В распределённой системе самая дорогая операция – это shuffle, то есть пересылка данных между узлами кластера по сети. 5 миллионов строк едут по сети – это медленно и дорого.

RDD делает три shuffles – один на `sum`, один на `avg`, один на `min`. Spark ничего не знает про код – он просто выполняет три независимых задачи, каждая со своей пересылкой данных.

DataFrame делает один shuffle. Catalyst видит, что у нас три агрегата, и объединяет их в одну операцию. При этом он использует схему, которая называется partial + final aggregation – двухфазная агрегация.

Что это значит? Представьте, что у нас 8 воркеров.  
Фаза 1: каждый воркер агрегирует данные, которые лежат у него – считает свою частичную сумму, частичное среднее, частичный минимум, всё за один проход.  
Фаза 2: частичные результаты пересылаются по сети (один shuffle) и объединяются в финальный ответ. Всё это – три метрики в одном проходе.

Плюс к этому: DataFrame работает с данными в бинарном формате Tungsten и генерирует оптимизированный байт-код JVM – нет никакой сериализации Python-объектов, нет лишнего расхода памяти.

Вывод: когда вам нужно несколько агрегатов – `groupBy().agg(...)` будет не просто удобнее, но и на порядок быстрее.

## Кейс B: Оконные функции – Top-N в группе

Вторая задача: найти топ-4 записей в каждой группе. Это тоже частая задача – топ продаж, топ пользователей, топ транзакций по категории.

**DataFrame:**
```python
w = Window.partitionBy("key").orderBy(F.col("value").desc())
df.withColumn("rn", F.row_number().over(w)).filter(F.col("rn") < 5)
```

**RDD:**
```python
rdd.groupByKey().mapValues(lambda x: sorted(x, reverse=True)[:5])
```

**Результат:** DataFrame – 0.37 с, RDD – 3.92 с. Разница в 11 раз.

Разрыв меньше, чем в первом кейсе, но причина понятна из плана выполнения. Catalyst применил специальную оптимизацию – WindowGroupLimit.

Чтобы объяснить проще: представьте, что в каждой из 1000 групп по 5000 строк. Наивный подход – собрать все 5000 строк группы на один узел, отсортировать их, взять первые 4. Это значит: пересылаем 5000 строк, сортируем 5000 строк.

WindowGroupLimit говорит: "Стойте. Зачем пересылать все 5000? Давайте каждый воркер *у себя* сначала отберёт топ-4, и по сети пройдут только 4 строки от каждого воркера". После объединения финальная фильтрация берёт топ из этих небольших наборов.

Это та же идея, что и partial aggregation из кейса A – сначала локально уменьшить объём данных, потом перетащить по сети только нужное.

У RDD-варианта с `groupByKey()` такой оптимизации нет – он собирает все значения группы на один узел, что плохо и по памяти, и по времени.

## Кейс C: Вложенные типы – Struct и Array

Реальные данные часто приходят в JSON-формате: вложенные объекты, массивы. Третий кейс – работа с такими данными: у каждой строки есть поле-структура `meta` и поле-массив `values`, нужно "развернуть" массив в отдельные строки.

**DataFrame:**
```python
df.select("key", "meta.subid", F.explode("values").alias("value"))
```

**RDD:**
```python
rdd = df.rdd.map(lambda row: json.dumps({...}))
parsed = rdd.map(lambda s: json.loads(s))
           .flatMap(lambda d: [...]) 
```

**Результат:** DataFrame – 0.17 с, RDD – 11.38 с. Разница в 65 раз.

Это самый наглядный кейс. Посмотрим на RDD-реализацию: данные уже есть в Spark в нормальном формате. Но чтобы работать с ними в Python, мы *сначала* сериализуем их в JSON-строку (`json.dumps`), а *потом* парсим обратно (`json.loads`). На каждой из 5 миллионов строк – это чудовищно расточительно.

DataFrame работает с данными напрямую в бинарном формате Tungsten – поля структуры извлекаются как смещения в памяти, никакая сериализация не нужна. Физический план показывает, что вся обработка происходит в одной стадии, без единого shuffle:

```
*(1) Generate explode(values)
  +- *(1) Project [key, subid, values]
     +- *(1) Range
```

Префикс `*(1)` означает whole-stage codegen – весь пайплайн скомпилирован в один блок байт-кода и выполняется без накладных расходов.

Вывод: если данные уже в Spark – не надо вытаскивать их в Python и обратно. Используйте встроенные функции.

## SQL Кейсы

Теперь два кейса, где SQL может быть эффективнее "наивного" DataFrame.

**Кейс 1: Broadcast Join**

Join большой таблицы (5 млн строк) с маленькой (1000 строк). SQL с хинтом:
```sql
SELECT /*+ BROADCAST(small) */ b.key, count(*)
FROM big b JOIN small s ON b.key = s.key
GROUP BY b.key
```

Хинт `BROADCAST` говорит Spark: "Рассели маленькую таблицу на все воркеры". Каждый воркер получает полную копию `small` в памяти и выполняет join локально – большая таблица не перемещается по сети вообще. В физическом плане это `BroadcastHashJoin` – самый быстрый вид join.

DataFrame без хинта может выбрать другую стратегию. SQL-хинт даёт явный контроль над физическим планом.

**Кейс 2: CTE**

CTE (Common Table Expressions) – это синтаксис `WITH sub AS (...)`, который позволяет дать имя подзапросу и переиспользовать его. Выглядит так, будто подзапрос вычисляется один раз. Но план говорит обратное:

Spark раскрыл CTE в два независимых агрегата – подзапрос вычисляется дважды. Это происходит и с DataFrame без явного `cache()`.

Вывод: CTE – для читаемости, не для производительности. Если подзапрос нужен несколько раз – вызовите `.cache()`.

## Общий вывод

Три кейса, три победы DataFrame. Почему?

1. **Меньше shuffles** – Catalyst объединяет операции, RDD не умеет.
2. **Меньше проходов по данным** – несколько агрегатов за один раз.
3. **Нет сериализации Python** – бинарный формат Tungsten, JVM код.
4. **Специализированные оптимизации** – WindowGroupLimit, BroadcastHashJoin.

Практическое правило: начинайте с DataFrame/SQL. Опускайтесь к RDD только там, где данные не табличные или нужен очень низкоуровневый контроль. Всегда проверяйте `df.explain(True)` – это показывает реальный план и то, какие оптимизации сработали.

## Шпаргалка: что искать в explain(True)

| Что видите в плане | Что это значит |
|---|---|
| `HashAggregate (partial)` + один `Exchange` | Двухфазная агрегация, эффективно |
| `BroadcastExchange` + `BroadcastHashJoin` | Broadcast join, маленькая таблица разослана |
| `WindowGroupLimit (Partial/Final)` | Оптимизированный Top-N |
| `*(N) ...` (со звёздочкой) | Whole-stage codegen, весь блок скомпилирован |
| `AdaptiveSparkPlan` | AQE включён, план может меняться на лету |
| Несколько `Exchange` для одной агрегации | Несколько shuffles – возможно, нужно переписать |
