# Лекция 8 + ДЗ 8: Kafka и событийные пайплайны

## Главная идея
`Kafka` — не просто очередь сообщений, а распределенный commit log, вокруг которого строят высоконагруженные событийные пайплайны. Тема про то, как организовать потоковую обработку так, чтобы она была масштабируемой, отказоустойчивой и сохраняла порядок там, где он важен.

## Базовые сущности Kafka
- `message` — сообщение;
- `producer` — пишет сообщение;
- `consumer` — читает;
- `topic` — логическое имя потока;
- `partition` — физическое разбиение потока;
- `broker` — сервер Kafka;
- `consumer group` — группа совместного чтения;
- `segment` — кусок лога на диске;
- `offset` — позиция сообщения в партиции.

Главный смысл:
- масштабирование чтения и записи строится вокруг партиций;
- порядок гарантируется только внутри одной партиции.

## Producer: что важно
- в какой `topic` писать;
- какой использовать `key`;
- какую партицию выбирать;
- какой `acks` нужен;
- какая репликация;
- нужна ли компрессия.

Ключевой момент:
- `key` определяет, в какую партицию попадет сообщение;
- значит, через `key` мы управляем порядком внутри логического объекта.

## Consumer: что важно
- `group_id`;
- когда коммитить offset;
- как обрабатывать ретраи;
- какая модель доставки нужна.

## Как работает чтение
- consumer читает сообщения по offset;
- Kafka сама данные не “стирает после чтения” как классическая очередь;
- удаление задается политикой retention;
- разные consumer groups могут читать один и тот же topic независимо.

Это большой плюс Kafka как общего журнала событий.

## Репликация
Нужна для отказоустойчивости.

Надо помнить:
- `replication.factor`;
- `min.insync.replicas`;
- `acks=all`.

Если репликация настроена хорошо, сбой одного брокера не приводит к потере доступности потока.

## Паттерны взаимодействия
- `point-to-point` — больше похоже на очереди.
- `publish-subscribe` — один producer, много независимых групп потребителей.

Kafka особенно сильна во втором сценарии.

## Политики хранения
### delete
- старые данные удаляются по времени или объему.

### compact
- по ключу сохраняется последнее актуальное значение.

Это важный момент:
- `delete` полезен для событийных логов;
- `compact` полезен для топиков состояния.

## Семантики доставки
### At most once
- можно потерять сообщение;
- дубликатов меньше;
- надежность ниже.

### At least once
- сообщение может прийти повторно;
- зато потери маловероятны.

### Exactly once
- достигается сложнее;
- обычно требует идемпотентности и/или транзакций.

На практике большинство продовых систем живут в `at least once` + идемпотентный downstream.

## Транзакции в Kafka
Нужны, когда:
- читаем из одного topic;
- пишем в другой;
- хотим избежать полупримененного состояния.

Это особенно важно в цепочках `Kafka -> Kafka`.

## KRaft и tiered storage
Из лекции:
- `KRaft` — современная модель управления метаданными без ZooKeeper.
- `Tiered Storage` — идея выносить старые сегменты на более дешевое хранилище.

Для экзамена достаточно понимать назначение:
- упрощение архитектуры;
- масштабирование хранения.

## Как мыслить про Kafka архитектурно
Нужно ответить на вопросы:
- по каким сущностям разделяем topic-и;
- что берем в key;
- сколько делаем партиций;
- где нужен порядок;
- где нужен replay;
- что хранить долго, что недолго;
- как обрабатывать ошибки.

## ДЗ 8: Kafka-пайплайн для Консультант Плюс
Это очень хороший прикладной кейс событийной архитектуры.

### Разбиение на topic-и
Предложены отдельные сырые потоки:
- законы;
- судебные решения;
- редакции документов.

Отдельно:
- нормализованный поток;
- topic актуального состояния;
- topic истории редакций;
- topic ссылок между документами;
- `DLQ`.

Почему это хорошо:
- разные бизнес-сущности и нагрузки не смешиваются;
- проще масштабировать и мониторить;
- проще задавать разные retention policy.

### Выбор ключей
- для законов и документов — `document_id`;
- для судебных дел — `case_id`;
- для редакций — `base_document_id`.

Это обеспечивает порядок событий внутри одного логического объекта.

### Партиционирование
Идея ДЗ:
- более нагруженные потоки получают больше партиций;
- потоки состояния и истории — меньше;
- `DLQ` — отдельный малый аварийный контур.

Важно понимать не конкретные числа, а принцип:
- партиции выбираются из сочетания нагрузки, желаемого параллелизма и стоимости overhead.

### Политики хранения из ДЗ
- `raw` топики -> `delete`, хранить ограниченное время;
- нормализованный поток -> тоже `delete`, но дольше для reprocessing;
- текущее состояние -> `compact`;
- история редакций -> `compact + delete`;
- `DLQ` -> `delete`.

Это очень сильное архитектурное решение: тип retention зависит от роли потока.

### Гарантии доставки
Рекомендуется:
- `enable.idempotence=true`;
- `acks=all`;
- `replication.factor=3`;
- `min.insync.replicas=2`;
- downstream должен быть идемпотентным.

Это классический продовый набор для надежной схемы `at least once`.

### Consumer groups
В ДЗ хорошо разделены независимые функции:
- нормализация;
- версионирование;
- извлечение связей;
- индексация поиска;
- аналитическая выгрузка;
- аварийное восстановление.

Смысл:
- разные потребители не мешают друг другу;
- Kafka выступает общей шиной событий.

## Что обязательно знать на экзамене
- Порядок в Kafka гарантируется только внутри партиции.
- Ключ управляет партицией, а значит и порядком.
- `offset` — это позиция чтения, а не уникальный ID события.
- `compact` нужен для текущего состояния, `delete` — для event log.
- `at least once` почти всегда требует идемпотентной обработки.
- `DLQ` — нормальная часть зрелой архитектуры.

## Короткий итог
Лекция 8 показывает Kafka как основу событийных данных. ДЗ отлично демонстрирует, как из абстрактных понятий `topic`, `partition`, `key`, `consumer group`, `retention` строится реальная архитектура для сложного юридического домена.
