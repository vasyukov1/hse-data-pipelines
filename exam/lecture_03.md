# Лекция 3 + ДЗ 3: файловые системы и форматы данных

## Суть темы
На физическом уровне архитектор данных решает два базовых вопроса:
1. Где физически лежат данные.
2. В каком формате они записаны.

Именно от этого зависят стоимость хранения, скорость чтения, возможность параллельной обработки и удобство эволюции схем.

## Зачем нужны распределенные файловые системы
Причины:
- объемы не помещаются на один сервер;
- нужна отказоустойчивость;
- нужна горизонтальная масштабируемость;
- вычисления выгодно приближать к данным.

## Основные варианты хранения
### HDFS
- Классическая файловая система Hadoop.
- Есть `NameNode` и `DataNode`.
- Хорошо встроена в экосистему Hadoop.

### Объектные хранилища
- `S3`, `GCS` и аналоги.
- Очень популярны в облаке.
- Дешево и удобно хранить большие объемы.
- Но у них другая модель, не как у классической POSIX/HDFS ФС.

### Apache Ozone
- Комбинирует идеи HDFS и S3.
- Поддерживает `O3FS` и `S3 API`.
- Лучше подходит для объединения аналитики, сырых данных и облачных приложений.

Из лекции важно помнить: Ozone рассматривался как хороший фундамент для lakehouse-архитектуры.

## Как выбирать формат данных
Критерии:
- объем хранения;
- скорость чтения и записи;
- наличие схемы;
- поддержка эволюции схемы;
- совместимость с инструментами;
- `splittability`, то есть возможность читать файл параллельно по частям.

`Splittability` очень важен для распределенной обработки: если файл нельзя эффективно разделить, параллелизм падает.

## Форматы и их смысл
### CSV / TSV
Плюсы:
- простота;
- человекочитаемость;
- универсальность.

Минусы:
- нет схемы;
- слабая типизация;
- лишний текстовый overhead;
- не лучший формат для big data.

Use case: маленькие объемы, ручной обмен, простая интерпретация.

### JSON
Плюсы:
- умеет вложенность;
- широко используется в API и логах;
- гибок.

Минусы:
- большой размер;
- нет строгой схемы по умолчанию;
- чтение и парсинг дороже;
- для аналитики часто невыгоден.

Use case: события, HTTP/API, полуструктурированные данные.

### Avro
Плюсы:
- схема в данных или рядом;
- поддержка schema evolution;
- удобно для стриминга и логов;
- `splittable`;
- хорошо подходит для построчной сериализации.

Минусы:
- не так хорош для аналитических сканов, как колонночные форматы.

Use case: потоковые события, обмен между системами, ingestion.

### Protobuf
Плюсы:
- бинарный;
- компактный;
- строгая схема;
- очень удобен для RPC и межсервисного обмена.

Минусы:
- не очень удобен для ad-hoc аналитики;
- не ориентирован на файловую аналитику.

Use case: микросервисы, RPC, событийные контракты.

### Parquet
Плюсы:
- колонночный формат;
- эффективное сжатие;
- `predicate pushdown`;
- хорош для фильтров, агрегаций и аналитики.

Минусы:
- хуже подходит для частых построчных изменений;
- не идеален для очень сложных или произвольных структур.

Use case: аналитические витрины, lakehouse, OLAP.

### ORC
- Тоже колонночный формат.
- Исторически силен в Hive-экосистеме.
- Сейчас часто проигрывает Parquet по популярности и экосистеме.

### SequenceFile
- Hadoop-специфичный формат для `key-value`.
- Сейчас скорее нишевый и исторический.

## Гибридные подходы
Лекция отдельно упоминала `Parquet + Protobuf`:
- аналитические поля хранятся колонками;
- сложный полезный payload хранится бинарным blob.

Смысл:
- сохранить аналитическую эффективность;
- не потерять сложную внутреннюю структуру.

Минус:
- архитектура сильно усложняется.

## Паттерны доступа и правильный формат
- `OLAP / агрегации` -> `Parquet`.
- `Streaming / частые записи / evolution` -> `Avro`.
- `RPC / межсервисная коммуникация` -> `Protobuf`.
- `Сложные структуры + аналитика` -> гибрид.

## Сжатие и блоки
Из лекции:
- `GZIP` — лучше сжатие, медленнее.
- `Snappy` — быстрее, хуже коэффициент сжатия.
- `ZSTD` — хороший компромисс.

Размер блоков — это компромисс:
- крупнее блоки -> лучше последовательное чтение, меньше overhead;
- мельче блоки -> выше параллелизм.

## Почему не решить все через классическую БД
- Не все big data задачи хорошо ложатся на СУБД.
- Полуструктурированные и огромные данные там хранить дорого и неудобно.
- Но транзакционные системы все равно нужны для OLTP.

Именно поэтому появляются связки `OLTP + Lake/Lakehouse`.

## ДЗ 3: сравнение форматов Parquet, Avro и JSON
В домашнем задании сравнивались:
- время записи;
- размер на диске;
- full scan;
- фильтрация по дате;
- простая агрегация.

### Что показал эксперимент
- `Parquet` обычно лучше всего в аналитических сценариях:
  - меньше весит;
  - быстрее фильтруется;
  - быстрее аггрегируется.
- `Avro` хорошо подходит как компромисс для сериализации и стриминга.
- `JSON` удобен как человекочитаемый и совместимый формат, но проигрывает по размеру и скорости.

### Почему Parquet выигрывает в аналитике
- колонночность;
- лучшее сжатие;
- чтение только нужных колонок;
- pushdown по фильтрам.

### Когда JSON все равно оправдан
- если главное — простота интеграции;
- если данные краткоживущие;
- если это лог или обменный формат, а не основное аналитическое хранилище.

## Что надо уметь объяснить на экзамене
- Почему `Parquet` лучше для `GROUP BY` и фильтрации.
- Почему `Avro` удобен для стриминга и schema evolution.
- Почему `JSON` плохо масштабируется как основной аналитический формат.
- Что такое `splittability` и почему это важно.
- Как соотносятся формат данных и паттерн доступа.

## Короткий итог
Лекция 3 учит: формат нельзя выбирать “по привычке”. Формат — это архитектурное решение под конкретный способ чтения и записи. ДЗ подтверждает это экспериментально: для аналитики выигрывает `Parquet`, для обмена и стриминга разумен `Avro`, а `JSON` удобен, но дорог по эффективности.
