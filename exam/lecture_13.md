# Лекция 13 + ДЗ 13: мониторинг data platform на Prometheus + Grafana

## Главная идея
Без мониторинга пайплайн “существует до первого сбоя”. Мониторинг нужен не только чтобы видеть, что что-то сломалось, но и чтобы:
- понимать деградации;
- контролировать ресурсы;
- вовремя реагировать;
- оценивать стоимость и эффективность.

Лекция объясняет основы метрик и Prometheus, а ДЗ строит архитектуру мониторинга для Kubernetes-кластера с микросервисами и Spark-job.

## Зачем нужен мониторинг
- оповещения в реальном времени;
- ускорение расследования инцидентов;
- управление нагрузкой;
- оценка расходов;
- аналитика по системе.

## Метрики vs логи
### Логи
- детальны;
- описывают события поштучно;
- удобны для расследования;
- хуже масштабируются как единый источник состояния.

### Метрики
- это агрегированная картина;
- хорошо подходят для алертов и графиков;
- не дают всех деталей.

Правильный ответ на экзамене:
- это не взаимоисключающие подходы;
- метрики и логи нужны вместе.

## Push vs Pull
### Push
- клиент сам отправляет данные.

### Pull
- сервер мониторинга сам приходит за метриками.

Для Prometheus базовая модель — `pull`.

Плюсы:
- проще дебажить;
- Prometheus контролирует scrape;
- единая модель для многих сервисов.

## TSDB
Для метрик нужна `Time Series Database`.

Данные вида:
- время;
- значение;
- набор labels.

Prometheus одновременно:
- собирает метрики;
- хранит их как time series;
- умеет выполнять запросы;
- умеет алертить.

## Формат метрик Prometheus
Типы:
- `Counter` — только растет, подходит для количества событий.
- `Gauge` — может расти и падать, подходит для текущего состояния.
- `Histogram` — распределение наблюдений, удобно для latency и percentiles.

Надо четко понимать, какой тип под какую задачу подходит.

## Labels
Labels — это измерения метрики:
- сервис;
- instance;
- namespace;
- job;
- статус ответа;
- окружение.

Но важно:
- слишком высокая кардинальность labels убивает Prometheus.

Пример плохой идеи:
- label с `user_id` или `request_id`.

## PromQL
Базовые вещи, которые надо помнить:
- instant vector;
- range vector;
- фильтрация по labels;
- `sum by (...)`;
- `sum without (...)`;
- `rate(...)` для counter;
- `delta(...)` для gauge.

### `rate()`
- считает скорость прироста;
- использовать с `Counter`;
- учитывает сброс после рестарта.

### `delta()`
- считает изменение значения за интервал;
- использовать с `Gauge`.

## Алерты
Сильная сторона мониторинга — автоматическая реакция.

Хороший alert должен иметь:
- четкое условие;
- серьезность;
- описание;
- понимание возможных ложных срабатываний.

Идея:
- не алертить “на все подряд”;
- алерты должны быть actionable.

## Безопасность /metrics
Лекция отдельно напоминает:
- можно отдавать метрики на отдельном порту;
- ограничивать доступ;
- настраивать аутентификацию;
- не делать endpoint публичным без причин.

## Персистентность и сброс счетчиков
После рестарта приложения счетчики часто сбрасываются в ноль.

Это нормально для `Counter`, если использовать `rate()`.

Нужно понимать:
- рестарты не обязательно означают потерю интерпретируемости метрики;
- но это надо учитывать в запросах.

## ДЗ 13: мониторинг Kubernetes + Spark
В ДЗ спроектирована архитектура на базе:
- `Prometheus`;
- `Grafana`;
- `Alertmanager`;
- `Pushgateway`;
- `kube-state-metrics`;
- `node-exporter`.

## Почему это хорошая архитектура
### Prometheus
- сбор и хранение метрик;
- центральная TSDB.

### Grafana
- визуализация и дашборды.

### Alertmanager
- маршрутизация уведомлений и управление алертами.

### kube-state-metrics / node-exporter
- инфраструктурные метрики кластера и узлов.

### Pushgateway
- особенно важен для короткоживущих batch-задач.

## Проблема short-lived jobs
Обычный `pull` плохо работает, если job живет слишком мало:
- Prometheus может просто не успеть сделать scrape.

Решение:
- job пушит итоговые метрики в `Pushgateway`;
- Prometheus потом scrapes Pushgateway.

Это очень важный вопрос для Spark и batch-пайплайнов.

## Что обязательно включать в мониторинг data platform
### Инфраструктура
- состояние нод;
- CPU / RAM / disk;
- состояние pod-ов;
- рестарты;
- лимиты и requests.

### Приложения
- RPS;
- latency;
- error rate;
- queue lag;
- размеры batch;
- время выполнения job.

### Spark / batch
- количество успешных / упавших job;
- длительность;
- объем обработанных данных;
- stage/task failures;
- backlog / last successful run.

### Бизнесовые метрики
- сколько документов обработано;
- сколько событий попало в DLQ;
- сколько данных поступило за период;
- SLA готовности витрин.

## Дашборды
Из постановки ДЗ важно уметь назвать хотя бы три типа:
- здоровье платформы;
- производительность Spark / batch;
- бизнесовые показатели пайплайна.

## Алерты
Из ДЗ важно не только “придумать правила”, а правильно мыслить:
- алерт на ошибку ingestion;
- алерт на рост latency;
- алерт на отсутствие успешных batch-run;
- алерт на переполнение ресурсов;
- алерт на рост DLQ.

Нужно уметь обсуждать и ложные срабатывания:
- короткие всплески;
- деплой;
- временная недоступность scrape target;
- отложенный batch.

## Что надо знать на экзамене
- Разницу между логами и метриками.
- Почему Prometheus обычно работает по `pull`.
- Чем `Counter` отличается от `Gauge`.
- Когда использовать `rate()`.
- Почему высокая кардинальность labels опасна.
- Зачем нужен `Pushgateway`.
