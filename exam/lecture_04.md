# Лекция 4 + ДЗ 4: MapReduce и почему иногда нужен RDD

## О чем тема
Лекция объясняет фундамент распределенных вычислений через `MapReduce`: почему данные нельзя было просто переносить по сети, как строится модель `map -> shuffle -> reduce`, и почему у нее есть ограничения. ДЗ затем показывает кейс, где низкоуровневый `RDD` может быть уместнее, чем `DataFrame`.

## Исторический контекст MapReduce
Основная проблема эпохи раннего big data:
- данные огромные;
- сеть медленная;
- сбои постоянны;
- чтение и запись на диск дорогие.

Ключевая идея:
- выгоднее отправить код к данным, чем гонять сами данные по сети.

Это принцип “move compute to data”.

## Контракт MapReduce
### Map
- Берет одну входную запись `(K1, V1)`.
- Преобразует ее в набор промежуточных `(K2, V2)`.
- Ничего не знает о других записях.

### Shuffle + Sort
- Группирует все значения по ключу.
- Это самое дорогое место:
  - сеть;
  - диск;
  - сортировка;
  - сериализация.

### Reduce
- Для каждого `K2` получает все связанные значения `Iterable<V2>`.
- Производит итоговые результаты `(K3, V3)`.

Главное запомнить: `Reduce` видит весь набор значений по ключу, а `Map` — только одну запись.

## Сильные стороны MapReduce
- Простой и мощный паттерн.
- Естественная масштабируемость.
- Хорошая отказоустойчивость.
- Подходит для batch-задач и однотипных проходов по большим данным.

## Слабые стороны MapReduce
- Каждая стадия материализуется на диск.
- Итеративные алгоритмы работают плохо.
- Длинные цепочки вычислений неудобны.
- Много шаблонного кода.
- Высокая задержка между стадиями.

Именно это в лекции формулируется как причина, почему MapReduce “убили” более современные движки вроде Spark.

## Почему Spark вытеснил чистый MapReduce
- вычисления в памяти;
- DAG из нескольких трансформаций;
- меньше промежуточной записи на диск;
- удобнее API;
- быстрее iterative workloads.

Но понимать MapReduce важно, потому что:
- это основа для понимания `shuffle`;
- многие принципы распределенных вычислений остались теми же.

## Связь с RDD
`RDD` в Spark во многом наследует мышление MapReduce:
- явные трансформации;
- контроль над логикой обработки;
- понимание партиций и шифлов;
- работа ближе к данным и к вычислительной модели.

## ДЗ 4: кейс, где RDD лучше подходит, чем DataFrame
В домашнем задании выбран реалистичный кейс анализа футбольных матчей:
- поток кадров каждые `40 ms`;
- десятки миллионов кадров на матч;
- данные о мяче, игроках, скорости, владении;
- задача — находить “опасные атаки” как последовательности состояний.

### Почему задача неудобна для DataFrame
- Это не просто SQL-агрегация.
- Нужно анализировать последовательность кадров.
- Нужно сохранять состояние автомата:
  - перехват;
  - контратака;
  - развитие эпизода;
  - завершение.
- Важны порядок, контекст и контроль памяти.

### Почему RDD здесь уместен
- Можно явно управлять разбиением и порядком обработки.
- Проще реализовать stateful-логику на уровне итератора по партиции.
- Гибче работать с нестандартными входами, включая бинарные логи.
- Можно в одном проходе получать несколько выходных артефактов.

### Сильный тезис из ДЗ
`DataFrame` не “всегда лучше”. Он лучше там, где задача хорошо ложится на табличную декларативную модель. Когда задача ближе к алгоритму обработки последовательностей и автоматам состояний, `RDD` может быть естественнее.

## Что важно уметь объяснить на экзамене
- Почему `shuffle` дорогой.
- Почему запись на диск между стадиями тормозит `MapReduce`.
- Почему итеративные вычисления плохо ложатся на старую модель.
- В каких случаях `RDD` все еще разумен:
  - нет табличной формы;
  - нужна очень нестандартная логика;
  - важен точный контроль обработки;
  - нужно обходить данные алгоритмически, а не декларативно.

## Типичный вопрос-ловушка
“Если есть DataFrame, зачем вообще знать RDD и MapReduce?”

Хороший ответ:
- потому что все дорогие операции Spark по сути упираются в те же физические проблемы: `shuffle`, сериализация, локальность, партиционирование, память;
- а часть задач по-прежнему алгоритмические, а не табличные.

## Короткий итог
Лекция 4 дает фундамент распределенных вычислений через MapReduce. ДЗ показывает, что старый низкоуровневый взгляд на данные не умер: для сложной stateful-обработки последовательностей `RDD` и сегодня может быть лучшим выбором.
