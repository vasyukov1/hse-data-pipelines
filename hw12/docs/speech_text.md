# Speech Text

Здравствуйте. Я покажу домашнее задание по лекции 12, в котором нужно было спроектировать структуру репозитория и полный путь развёртывания разнородных приложений в Kubernetes.

Я сделал единый учебный репозиторий в каталоге `hw12`, чтобы в одном месте были видны и код приложений, и инфраструктура, и файлы запуска. Внутри я разделил проект на несколько крупных частей.

Первая часть — это `apps`. Там лежат исходники самих приложений. Я сделал два примера. Первый — это Spark-задача `orders_daily`, которая читает CSV с заказами, агрегирует данные по дате и товару и пишет результат в JSON. Второй пример — это витрина `sales_dashboard` на React. Она показывает среду, путь к данным и несколько показателей.

Вторая часть — это `deploy/helm`. Здесь лежат обёртки над внешними Helm-чартами. Я выбрал четыре платформенных компонента: `Argo Workflows`, `Spark Operator`, `MinIO` и `PostgreSQL`. То есть я не складывал чужие длинные манифесты в репозиторий вручную, а описал их как зависимости Helm. Это даёт версионирование, понятную настройку через `values.yaml` и простой откат через `helm rollback`.

Третья часть — это `deploy/kustomize`. Здесь находится развёртывание собственной витрины. Для своих сервисов я выбрал именно Kustomize, потому что он оставляет манифесты обычными YAML-файлами и хорошо показывает разницу между средами. У меня есть `base`, а поверх него два оверлея: `dev` и `prod`. В них меняются теги образов, число реплик и значения runtime-конфигурации.

Четвёртая часть — это `argo/templates` и `argo/workflows`. Здесь находится логика запуска Spark-задачи через Argo Workflows. Я сохранил идею из прошлого задания: вместо одного большого workflow использую переиспользуемые шаблоны. У меня есть шаблон, который создаёт `SparkApplication`, шаблон, который ждёт завершения Spark-задачи, и шаблон, который формирует итоговый отчёт. А конкретный `CronWorkflow` просто связывает их в DAG и передаёт параметры.

Теперь о выборе CI/CD. Сборку контейнеров я вынес в `GitLab CI`. Для задания это удобный вариант, потому что он естественно стартует от `git push`, хранит историю запусков и позволяет разделить процесс на этапы. В моём примере стадии такие: сначала проверка, потом сборка образов, потом генерация workflow, потом развёртывание.

На стадии проверки запускаются `go test` для утилиты генерации workflow, синтаксическая проверка Python-кода Spark-задачи, генерация итоговых YAML-файлов и рендер Kustomize. То есть ошибки в конфигурации можно поймать ещё до публикации образов.

Дальше идёт стадия сборки. Там через `kaniko` собираются два образа: образ Spark-задачи и образ витрины. После сборки они публикуются в `GitLab Container Registry`. Это и есть основное хранилище контейнерных артефактов. Для сгенерированных workflow-файлов я использую артефакты GitLab CI и каталог `argo/workflows/generated`, чтобы итоговый YAML тоже был воспроизводимым и видимым.

Отдельно скажу про генерацию workflow. Я сделал небольшую утилиту на Go `workflowgen`. Она читает шаблон `CronWorkflow` и YAML с параметрами среды. На выходе получается готовый файл, например `orders-daily-dev`. Это полезно по двум причинам. Во-первых, шаблон и значения среды разделены. Во-вторых, конкретный итоговый YAML можно сохранить как артефакт пайплайна и при необходимости быстро применить или откатить.

Как происходит запуск в кластере. Сначала применяются служебные манифесты: пространства имён и права для Spark-драйвера. Потом через `helm upgrade --install` разворачиваются Argo Workflows, Spark Operator, MinIO и PostgreSQL. Затем через `kubectl apply` в кластер загружаются `WorkflowTemplate` и уже сгенерированный `CronWorkflow`. После этого контроллер Argo видит новый объект в Kubernetes API и начинает выполнять его по расписанию. То есть Argo не читает файлы с диска, а реагирует именно на объекты в кластере.

Плюсы выбранной схемы такие. Первый плюс — переиспользование. Один и тот же шаблон запуска Spark можно применять для разных задач, меняя только образ, пути к данным и расписание. Второй плюс — изоляция сред. Различия между `dev` и `prod` не спрятаны в случайных скриптах, а явно лежат в `values` и `overlays`. Третий плюс — откат. Для внешних систем это `helm rollback`, для своих витрин это возврат коммита с Kustomize-патчами, для Spark-задачи это возврат старого тега образа и повторная генерация workflow.

Для воспроизводимости я добавил скрипты. `verify.sh` прогоняет локальные проверки. `render-helm.sh` скачивает локальный `helm`, подтягивает зависимости и рендерит манифесты. `generate-workflows.sh` собирает готовые YAML-файлы для `dev` и `prod`. То есть проект можно не только описать, но и реально прогнать по шагам.

Если подвести итог, то в этой работе я показал единый каркас платформы данных в Kubernetes, где внешняя инфраструктура ставится через Helm, собственные интерфейсы разворачиваются через Kustomize, а вычислительные Spark-задачи запускаются через Argo Workflows и Spark Operator. При этом весь путь от изменения в Git до появления объекта в кластере описан явно и воспроизводимо.
