# Отчёт по домашнему заданию 12

## 1. Постановка задачи

Нужно было спроектировать структуру репозитория и полный путь развёртывания разнородных приложений в Kubernetes:

- Spark-задач для обработки данных;
- сторонних платформенных компонентов из Helm;
- внутренних витрин.

## 2. Архитектурное решение

Я выбрал схему с одним репозиторием, потому что для учебного задания она проще для чтения и нагляднее показывает весь поток целиком.

Разделение сделано по типам сущностей:

- `apps/` хранит исходники приложений;
- `deploy/helm/` хранит обёртки над внешними Helm-чартами;
- `deploy/kustomize/` хранит развёртывание собственных приложений;
- `argo/templates/` хранит переиспользуемые шаблоны Argo;
- `argo/workflows/templates/` хранит шаблоны конкретных запусков;
- `argo/workflows/generated/` хранит уже собранный YAML, который можно применять в кластер.

## 3. Технологический стек

### 3.1. Сборка контейнеров

Выбран `GitLab CI`:

- он хорошо сочетается с `git push`, merge request и защищёнными ветками;
- можно прозрачно хранить журнал всех запусков;
- можно отдельно фиксировать артефакты проверки и генерации;
- `kaniko` позволяет собирать контейнеры прямо в CI.

### 3.2. Хранение артефактов

- Контейнеры: `GitLab Container Registry`.
- Сгенерированные `Workflow`-файлы: артефакты GitLab CI и каталог `argo/workflows/generated/`.
- Обработанные данные: `MinIO`.
- Табличные данные для витрин и служебных задач: `PostgreSQL`.

## 4. Почему Helm и Kustomize разделены

### Helm для сторонних систем

Helm я использую для:

- `Argo Workflows`;
- `Spark Operator`;
- `MinIO`;
- `PostgreSQL`.

Причины:

- сторонние продукты уже поставляются как удобные Helm-чарты;
- легко версионировать и откатывать релизы;
- параметры удобно выносить в `values.yaml`.

### Kustomize для своих приложений

Kustomize я использую для витрины `sales-dashboard`.

Причины:

- манифесты остаются обычными YAML-файлами без лишней шаблонизации;
- различия между `dev` и `prod` видны как точечные патчи;
- удобно поддерживать GitOps-подход.

## 5. Переиспользование шаблонов Argo

В `hw12` я перенёс подход сборки пайплайна из универсальных шаблонов на запуск Spark-задач:

- `spark-submit-template.yaml` создаёт объект `SparkApplication`;
- `spark-wait-template.yaml` ждёт завершения задачи;
- `report-template.yaml` выпускает итоговый отчёт о запуске.

За счёт этого конкретный `CronWorkflow` не содержит сложной логики. Он лишь связывает готовые шаблоны и передаёт им параметры.

## 6. Как устроен путь от push до запуска

### Шаг 1. Проверка

GitLab CI запускает:

- `go test ./...` для утилиты генерации;
- `python3 -m py_compile` для Spark-кода;
- генерацию итогового `Workflow`;
- рендер `Kustomize`.

На этом шаге удобно отлавливать ошибки ещё до сборки контейнеров.

### Шаг 2. Сборка образов

Отдельно собираются:

- образ Spark-задачи `orders-daily`;
- образ витрины `sales-dashboard`.

В образ Spark включён код `job.py` и тестовый набор данных. Это удобно для демонстрации.

### Шаг 3. Генерация workflow

Файл `cmd/workflowgen/main.go` читает:

- шаблон `orders-daily-workflow.tpl.yaml`;
- параметры среды, например `orders-daily-dev.values.yaml`.

На выходе получается готовый `CronWorkflow`, который уже можно применять в кластер.

Это даёт два плюса:

- конкретный YAML версионируется как результат генерации;
- шаблон и значения среды разделены.

### Шаг 4. Развёртывание платформы

Сначала применяются свои базовые ресурсы:

- пространства имён;
- сервисный аккаунт и роли для Spark-драйвера.

Потом через Helm ставятся:

- Argo Workflows;
- Spark Operator;
- MinIO;
- PostgreSQL.

После этого загружаются `WorkflowTemplate` и создаётся конкретный `CronWorkflow`.

### Шаг 5. Как Argo подхватывает workflow

Argo Workflows не читает YAML из каталога напрямую. Он следит за объектами Kubernetes API.

Поэтому схема такая:

1. GitLab CI генерирует YAML.
2. GitLab CI выполняет `kubectl apply -f`.
3. В кластере появляется объект `CronWorkflow`.
4. Контроллер Argo замечает объект и начинает его исполнять по расписанию.

## 7. Что делает Spark-задача

Задача `orders_daily`:

- читает CSV с заказами;
- преобразует дату;
- считает число заказов и сумму по дням и товарам;
- пишет результат в JSON.

Этот пример достаточно маленький для учебной работы и при этом показывает реальную механику запуска через Spark Operator.

## 8. Что делает витрина

Витрина `sales-dashboard` показывает:

- среду;
- источник данных;
- частоту обновления;
- несколько показателей.

Ключевая идея в том, что параметры среды не вшиваются в образ, а приходят из `ConfigMap`, который меняется через `Kustomize`.

## 9. Преимущества выбранной схемы

### Переиспользование

Шаблоны Argo можно использовать для других Spark-задач. Достаточно:

- заменить имя образа;
- заменить путь к входу и выходу;
- при необходимости поправить расписание.

### Версионирование

Есть три независимых слоя версий:

- версия кода приложения;
- версия контейнерного образа;
- версия конфигурации развёртывания.

Это сильно упрощает анализ изменений.

### Изоляция сред

`dev` и `prod` отличаются:

- тегами образов;
- путями к данным;
- частотой запуска;
- количеством реплик витрины.

Изоляция оформлена явными файлами, а не скрытыми переменными в случайных скриптах.

### Откат

- Для сторонней платформы используется `helm rollback`.
- Для витрины можно вернуть нужный коммит с Kustomize-патчами.
- Для Spark-задачи достаточно вернуть прошлый тег образа и заново сгенерировать `CronWorkflow`.
