# Архитектурная документация системы мониторинга

## 1. Введение

### 1.1. Цель документа

Документ описывает проект системы мониторинга для Kubernetes-кластера, в котором работают долгоживущие микросервисы и batch-джобы Apache Spark.

Система мониторинга строится на базе:

- **Prometheus** — сбор, хранение и запрос метрик
- **Grafana** — визуализация метрик на дашбордах
- **Alertmanager** — отправка уведомлений по алертам
- **Pushgateway** — сбор итоговых метрик от короткоживущих batch-задач
- **kube-state-metrics** и **node-exporter** — сбор инфраструктурных метрик Kubernetes.

Главная задача мониторинга — быстро понять, что в системе работает нормально, что деградирует, а что требует вмешательства.

---

### 1.2. Что проектируется

Проектируется мониторинг платформы для загрузки и обработки статей. Пользователь загружает статью на сайт, после чего система сохраняет файл, ставит задачу на обработку, запускает batch-обработку в Spark и публикует результат.

В системе есть два типа нагрузки:

1. **Долгоживущие микросервисы**  
   Это обычные backend-сервисы, которые постоянно работают в Kubernetes и обрабатывают HTTP-запросы.

2. **Batch-джобы Spark**  
   Это периодические задачи, которые запускаются по расписанию или по событию, обрабатывают данные и завершаются.

Такое разделение важно, потому что микросервисы можно регулярно опрашивать через `/metrics`, а короткие Spark-jobs могут завершиться раньше, чем Prometheus успеет забрать с них метрики.

## 2. Описание системы

### 2.1. Основные компоненты

| Компонент | Тип | Назначение |
|---|---|---|
| `api-gateway` | Микросервис | Принимает HTTP-запросы от frontend-приложения |
| `auth-service` | Микросервис | Отвечает за авторизацию пользователей |
| `article-service` | Микросервис | Хранит информацию о статьях и их статусах |
| `upload-service` | Микросервис | Принимает файлы статей и сохраняет их в объектное хранилище |
| `processing-service` | Микросервис | Создаёт задачи на обработку статей |
| `Kafka` | Брокер сообщений | Передаёт события между сервисами |
| `PostgreSQL` | База данных | Хранит пользователей, статьи, статусы обработки |
| `S3/MinIO` | Объектное хранилище | Хранит загруженные файлы статей |
| `article-etl-job` | Spark job | Основная batch-обработка статей |
| `recommendation-job` | Spark job | Пересчёт рекомендаций |
| `quality-check-job` | Spark job | Проверка качества и дубликатов статей |

---

### 2.2. Основной пользовательский сценарий работы

1. Пользователь загружает статью через frontend.
2. `api-gateway` принимает запрос и передаёт его в `upload-service`.
3. `upload-service` сохраняет файл в S3/MinIO.
4. `article-service` создаёт запись о статье в PostgreSQL.
5. `processing-service` отправляет событие в Kafka.
6. Spark job забирает данные на обработку.
7. После завершения обработки статья получает статус `processed` или `failed`.
8. Результат отображается пользователю.

Для мониторинга важно видеть не только техническое состояние сервисов, но и сам бизнес-процесс: загружаются ли статьи, обрабатываются ли они, сколько ошибок возникает, не растёт ли очередь обработки.

---

## 3. Цели мониторинга

1. **Контроль доступности сервисов**  
   Нужно видеть, какие сервисы работают, какие недоступны, какие часто перезапускаются.

2. **Контроль производительности API**  
   Нужно отслеживать RPS, latency, долю HTTP 5xx и HTTP 4xx ошибок.

3. **Контроль состояния Kubernetes-кластера**  
   Нужно отслеживать CPU, RAM, рестарты pod'ов, состояние контейнеров и доступность Prometheus targets.

4. **Контроль Spark batch-обработки**  
   Нужно видеть, запускались ли Spark-jobs, успешно ли они завершились, сколько времени заняли, сколько задач упало.

5. **Контроль бизнес-показателей**  
   Нужно знать, сколько статей загружается, сколько успешно обрабатывается, какая доля ошибок и не растёт ли очередь обработки.

6. **Автоматическое оповещение об инцидентах**  
   Важные проблемы должны попадать в Alertmanager и отправляться ответственным людям.

### 4.2. Сбор метрик

Prometheus использует pull-подход: он сам периодически приходит к приложениям и забирает метрики по HTTP.

Для микросервисов это выглядит так:

```text
Prometheus -> GET /metrics -> microservice
```

Каждый микросервис держит в памяти текущие значения метрик: количество запросов, количество ошибок, длительность обработки запросов и другие показатели. Prometheus периодически забирает эти значения и сохраняет их во временную базу данных.

Для Kubernetes-инфраструктуры используются специальные exporters:

- `kube-state-metrics` отдаёт состояние Kubernetes-объектов: pod, deployment, job, container
- `node-exporter` отдаёт метрики узлов: CPU, RAM, disk, network
- container metrics используются для анализа потребления ресурсов контейнерами.

Для Spark есть два варианта:

1. Если Spark job работает долго, Prometheus может собирать метрики с driver/executor подов.
2. Если Spark job короткая, она отправляет итоговые метрики в Pushgateway, а Prometheus уже забирает их оттуда.

---

### 4.3. Pushgateway

Prometheus сам приходит за метриками по расписанию. Например, раз в 30 секунд. Если Spark job живёт 10 секунд, Prometheus может её вообще не увидеть.

Пример:

```text
00:00 — Spark job стартовала
00:10 — Spark job завершилась
00:30 — Prometheus пришёл за метриками, но pod уже удалён
```

Чтобы не потерять результат такой job'ы, она в конце работы отправляет итоговые метрики в Pushgateway:

```text
Spark job -> Pushgateway -> Prometheus -> Grafana / Alertmanager
```

В Pushgateway нужно отправлять только финальные batch-метрики:

- job завершилась успешно или нет
- сколько времени она выполнялась
- сколько записей обработала
- когда был последний успешный запуск
- сколько ошибок было найдено.

## 5. Источники метрик

### 5.1. Микросервисы

Каждый микросервис публикует endpoint `/metrics`.

Пример:

```text
http://article-service:9090/metrics
http://upload-service:9090/metrics
http://processing-service:9090/metrics
```

Сервисные метрики нужны для ответа на вопросы:

- сколько запросов приходит в сервис
- какие ручки самые нагруженные
- сколько ошибок возвращает сервис
- насколько быстро сервис отвечает
- не ухудшилась ли производительность после релиза

---

### 5.2. Kubernetes

Kubernetes-метрики нужны для ответа на вопросы:

- хватает ли подам CPU и памяти
- не рестартуют ли контейнеры
- есть ли поды в `CrashLoopBackOff`
- доступны ли targets для Prometheus
- не перегружены ли ноды

---

### 5.3. Spark

Spark-метрики нужны для ответа на вопросы:

- запускалась ли batch-job
- успешно ли она завершилась
- сколько времени она выполнялась
- были ли failed stages или failed tasks
- не выросло ли время обработки
- не было ли проблем с executor'ами

---

### 5.4. Бизнес-метрики

Бизнес-метрики нужны, чтобы видеть состояние продукта, а не только инфраструктуры.

Например, может быть ситуация, когда все пды работают, CPU нормальный, HTTP 500 нет, но статьи перестали обрабатываться из-за проблемы в пайплайне. Без бизнес-метрик такая проблема может быть замечена поздно.

## 6. Ключевые метрики

### 6.1. Таблица метрик

| Метрика | Тип | Лейблы | Источник | Что показывает |
|---|---|---|---|---|
| `http_requests_total` | Counter | `service`, `method`, `route`, `status`, `namespace` | Микросервисы | Количество HTTP-запросов |
| `http_request_duration_seconds` | Histogram | `service`, `method`, `route`, `le` | Микросервисы | Распределение времени ответа API |
| `kube_pod_container_status_restarts_total` | Counter | `namespace`, `pod`, `container` | kube-state-metrics | Количество рестартов контейнеров |
| `container_cpu_usage_seconds_total` | Counter | `namespace`, `pod`, `container` | container metrics | Использование CPU контейнерами |
| `container_memory_working_set_bytes` | Gauge | `namespace`, `pod`, `container` | container metrics | Текущее использование памяти |
| `article_uploads_total` | Counter | `source`, `content_type`, `status` | upload-service | Количество загруженных статей |
| `article_processing_total` | Counter | `pipeline`, `stage`, `status` | processing-service / Spark | Количество обработанных статей |
| `article_processing_duration_seconds` | Histogram | `pipeline`, `stage`, `status`, `le` | processing-service / Spark | Время обработки статьи |
| `article_processing_queue_lag` | Gauge | `queue`, `consumer_group` | Kafka exporter / processing-service | Отставание очереди обработки |
| `spark_job_runs_total` | Counter | `job_name`, `namespace`, `status` | Spark / Pushgateway | Количество запусков Spark-job'ов |
| `spark_job_duration_seconds` | Histogram | `job_name`, `status`, `le` | Spark / Pushgateway | Длительность Spark-job'ов |
| `spark_stage_failed_tasks_total` | Counter | `app_name`, `stage_id`, `reason` | Spark metrics | Количество упавших Spark task'ов |
| `spark_executor_memory_used_bytes` | Gauge | `app_name`, `executor_id` | Spark metrics | Использование памяти executor'ами |
| `spark_job_last_success_timestamp_seconds` | Gauge | `job_name` | Spark / Pushgateway | Время последнего успешного запуска Spark-job |

---

### 6.2. Пояснение по типам метрик

#### Counter

`Counter` — счётчик, который только растёт. Например:

```text
http_requests_total
article_uploads_total
spark_job_runs_total
```

Counter подходит для количества событий: запросы, ошибки, запуски job'ов, обработанные статьи.

---

#### Gauge

`Gauge` — значение, которое может расти и уменьшаться. Например:

```text
container_memory_working_set_bytes
article_processing_queue_lag
spark_executor_memory_used_bytes
```

Gauge подходит для текущего состояния: память, размер очереди, количество активных задач.

---

#### Histogram

`Histogram` — распределение значений по бакетам. Например:

```text
http_request_duration_seconds
article_processing_duration_seconds
spark_job_duration_seconds
```

Histogram удобен для latency и duration, потому что по нему можно считать p95 и p99.

---

### 6.3. Важное правило по labels

В labels нельзя добавлять значения с высокой уникальностью:

- `user_id`
- `article_id`
- `request_id`
- `email`
- `file_name`
- `uuid`.

Это создаст слишком много временных рядов и может перегрузить Prometheus.

Хорошие labels:

- `service`
- `namespace`
- `method`
- `route`
- `status`
- `job_name`
- `pipeline`
- `stage`.

# 7.1. Dashboard: Kubernetes / System Health

## Назначение

Дашборд показывает состояние Kubernetes-кластера и подов. По нему можно быстро понять:

- не падают ли поды
- не растут ли рестарты
- хватает ли контейнерам CPU и RAM
- все ли targets доступны для Prometheus

---

## Панель 1. CPU usage по подам

```promql
sum by (namespace, pod) (
  rate(container_cpu_usage_seconds_total{container!="", image!=""}[5m])
)
```

**Что показывает:**  
Сколько CPU используют поды за последние 5 минут.

**Зачем нужно:**  
Если CPU резко вырос, сервис может начать медленнее отвечать.

---

## Панель 2. Memory usage по подам

```promql
sum by (namespace, pod) (
  container_memory_working_set_bytes{container!="", image!=""}
)
```

**Что показывает:**  
Текущее потребление памяти подами.

**Зачем нужно:**  
Если память постоянно растёт, возможна утечка памяти. Если pod превышает лимит, Kubernetes может завершить контейнер.

---

## Панель 3. Рестарты контейнеров за 15 минут

```promql
sum by (namespace, pod, container) (
  increase(kube_pod_container_status_restarts_total[15m])
)
```

**Что показывает:**  
Сколько раз контейнеры перезапускались за последние 15 минут.

**Зачем нужно:**  
Частые рестарты обычно означают ошибку в приложении, нехватку памяти или проблемы с конфигурацией.

---

## Панель 4. Недоступные Prometheus targets

```promql
up == 0
```

**Что показывает:**  
Какие targets Prometheus не смог собрать.

**Зачем нужно:**  
Если target недоступен, это может означать, что сервис упал, `/metrics` недоступен или настроен неправильный ServiceMonitor.

---

## Панель 5. Поды не в состоянии Running

```promql
sum by (namespace, pod, phase) (
  kube_pod_status_phase{phase!="Running"}
)
```

**Что показывает:**  
Поды, которые не находятся в нормальном состоянии `Running`.

**Зачем нужно:**  
Помогает быстро найти поды в `Pending`, `Failed`, `Unknown` и других проблемных состояниях.

---

# 7.2. Dashboard: Microservices / API Performance

## Назначение

Дашборд показывает состояние backend-сервисов ArticleFlow.

Он нужен, чтобы видеть:

- нагрузку на сервисы
- долю ошибок
- latency
- самые проблемные API-ручки.

---

## Панель 1. RPS по сервисам

```promql
sum by (service) (
  rate(http_requests_total[5m])
)
```

**Что показывает:**  
Количество HTTP-запросов в секунду по каждому сервису.

**Зачем нужно:**  
Помогает понять текущую нагрузку и увидеть аномальные всплески или падение трафика.

---

## Панель 2. Error rate по сервисам

```promql
100 *
sum by (service) (
  rate(http_requests_total{status=~"5.."}[5m])
)
/
sum by (service) (
  rate(http_requests_total[5m])
)
```

**Что показывает:**  
Процент HTTP 5xx ошибок по каждому сервису.

**Зачем нужно:**  
5xx означает серверную ошибку. Если доля 5xx растёт, проблема, скорее всего, находится в приложении, базе данных, очереди или внешней зависимости.

---

## Панель 3. p95 latency по сервисам

```promql
histogram_quantile(
  0.95,
  sum by (service, le) (
    rate(http_request_duration_seconds_bucket[5m])
  )
)
```

**Что показывает:**  
Время ответа, быстрее которого укладываются 95% запросов.

**Зачем нужно:**  
Среднее время ответа может скрывать проблемы. p95 лучше показывает, что происходит с медленными запросами.

---

## Панель 4. p99 latency по API-ручкам

```promql
histogram_quantile(
  0.99,
  sum by (service, route, le) (
    rate(http_request_duration_seconds_bucket[5m])
  )
)
```

**Что показывает:**  
Время ответа для самых медленных 1% запросов по конкретным API-ручкам.

**Зачем нужно:**  
Помогает найти конкретные endpoints, которые работают хуже остальных.

---

## Панель 5. Количество 4xx-ошибок

```promql
sum by (service, route, status) (
  rate(http_requests_total{status=~"4.."}[5m])
)
```

**Что показывает:**  
Скорость появления клиентских ошибок.

**Зачем нужно:**  
4xx не всегда означают проблему сервера, но резкий рост может говорить о сломанном frontend, изменении API-контракта или массовых ошибках пользователей.

---

# 7.3. Dashboard: Spark Batch Jobs

## Назначение

Дашборд показывает состояние Spark batch-обработки.

Он нужен, чтобы видеть:

- запускались ли job'ы
- успешно ли они завершались
- сколько времени занимала обработка
- есть ли failed tasks
- есть ли проблемы с executor'ами

---

## Панель 1. Запуски Spark-job'ов по статусу за 24 часа

```promql
sum by (job_name, status) (
  increase(spark_job_runs_total[24h])
)
```

**Что показывает:**  
Сколько раз каждая Spark-job запускалась за сутки и с каким результатом.

**Зачем нужно:**  
Позволяет быстро увидеть, какие job'ы выполнялись успешно, а какие падали.

---

## Панель 2. Failed Spark jobs за сутки

```promql
sum by (job_name) (
  increase(spark_job_runs_total{status="failed"}[24h])
)
```

**Что показывает:**  
Количество неуспешных запусков Spark-job'ов за последние 24 часа.

**Зачем нужно:**  
Это один из главных показателей состояния batch-обработки.

---

## Панель 3. p95 длительности Spark-job'ов

```promql
histogram_quantile(
  0.95,
  sum by (job_name, le) (
    rate(spark_job_duration_seconds_bucket[7d])
  )
)
```

**Что показывает:**  
p95 длительности Spark-job'ов за период.

**Зачем нужно:**  
Если job начала выполняться дольше обычного, это может означать рост объёма данных, data skew, проблемы с executor'ами или деградацию хранилища.

---

## Панель 4. Время с последнего успешного запуска

```promql
time() - max by (job_name) (
  spark_job_last_success_timestamp_seconds
)
```

**Что показывает:**  
Сколько секунд прошло с последнего успешного запуска каждой Spark-job.

**Зачем нужно:**  
Даже если job не падает явно, она может перестать запускаться. Эта метрика помогает найти такие случаи.

---

## Панель 5. Failed tasks по Spark stage

```promql
sum by (app_name, stage_id, reason) (
  increase(spark_stage_failed_tasks_total[1h])
)
```

**Что показывает:**  
Количество упавших Spark task'ов по stage и причине.

**Зачем нужно:**  
Помогает понять, где именно в Spark job возникает проблема: в чтении данных, shuffle, записи результата или отдельной трансформации.

---

## Панель 6. Использование памяти executor'ами

```promql
sum by (app_name) (
  spark_executor_memory_used_bytes
)
```

**Что показывает:**  
Сколько памяти используют executor'ы Spark-приложений.

**Зачем нужно:**  
Если памяти не хватает, Spark job может падать, работать медленно или часто пересчитывать данные.

# 7.4. Dashboard: Business Metrics

## Назначение

Дашборд показывает состояние бизнес-процесса обработки статей.

Он нужен, чтобы видеть:

- сколько статей загружается
- сколько статей успешно обрабатывается
- сколько статей падает с ошибкой
- не растёт ли очередь обработки
- сколько времени занимает обработка.

---

## Панель 1. Загруженные статьи за час

```promql
sum (
  increase(article_uploads_total[1h])
)
```

**Что показывает:**  
Сколько статей было загружено за последний час.

**Зачем нужно:**  
Позволяет видеть активность пользователей и резкие изменения нагрузки.

---

## Панель 2. Успешно обработанные статьи за час

```promql
sum (
  increase(article_processing_total{status="success"}[1h])
)
```

**Что показывает:**  
Сколько статей успешно обработано за последний час.

**Зачем нужно:**  
Если загрузки есть, а успешной обработки нет, значит проблема находится в processing pipeline.

---

## Панель 3. Доля успешной обработки

```promql
100 *
sum (
  rate(article_processing_total{status="success"}[5m])
)
/
sum (
  rate(article_processing_total[5m])
)
```

**Что показывает:**  
Процент успешно обработанных статей.

**Зачем нужно:**  
Это главный бизнес-показатель качества обработки.

---

## Панель 4. p95 времени обработки статьи

```promql
histogram_quantile(
  0.95,
  sum by (pipeline, le) (
    rate(article_processing_duration_seconds_bucket[5m])
  )
)
```

**Что показывает:**  
Сколько времени занимает обработка статьи в 95% случаев.

**Зачем нужно:**  
Если обработка стала медленнее, пользователи дольше ждут результата. Также это может говорить о проблемах в Spark, Kafka, S3 или базе данных.

---

## Панель 5. Lag очереди обработки

```promql
sum by (queue, consumer_group) (
  article_processing_queue_lag
)
```

**Что показывает:**  
Насколько обработчики отстают от входящего потока событий.

**Зачем нужно:**  
Если lag растёт, система не успевает обрабатывать статьи. Это может привести к задержкам публикации.

## 8. Alerting rules

Алерты должны срабатывать только на ситуации, которые требуют внимания. Если сделать слишком много шумных алертов, их начнут игнорировать.

В проекте используются уровни:

- `critical` — проблема уже влияет на работу системы или скоро повлияет
- `warning` — есть деградация, но сервис ещё может работать
- `info` — полезное уведомление, не требующее срочной реакции.

---

# 8.1. Alert: High HTTP Error Rate

## Назначение

Алерт срабатывает, если сервис начал часто возвращать HTTP 5xx.

## Пояснение

Если больше 5% запросов завершаются серверной ошибкой в течение 10 минут, это уже похоже на реальную проблему, а не на единичный сбой.

## Severity

`critical`

## Возможные причины

- ошибка после релиза
- недоступность PostgreSQL
- проблема с Kafka
- ошибка в конфигурации
- недоступность S3/MinIO
- превышение лимитов CPU/RAM

## Возможные ложные срабатывания

- очень маленький трафик
- ручное тестирование ошибочных сценариев
- canary deployment
- кратковременная недоступность зависимости

---

# 8.2. Alert: High API Latency

## Назначение

Алерт срабатывает, если p95 latency сервиса больше 1 секунды.

## Пояснение

p95 latency показывает, как долго ждут ответ медленные пользователи. Если p95 вырос, система может формально работать, но пользовательский опыт уже ухудшается.

## Severity

`warning`

## Возможные причины

- медленные SQL-запросы
- рост нагрузки
- нехватка CPU
- забитый connection pool
- задержки Kafka
- медленное объектное хранилище
- неудачный релиз.

## Возможные ложные срабатывания

- прогрев кешей после деплоя
- холодный старт сервиса
- низкое количество запросов
- временный всплеск нагрузки.

---

# 8.3. Alert: Pod Restarting Too Often

## Назначение

Алерт срабатывает, если контейнер часто рестартует.

## Пояснение

Больше трёх рестартов за 15 минут — это уже сильный сигнал, что контейнер находится в нестабильном состоянии.

## Severity

`critical`

## Возможные причины

- `CrashLoopBackOff`
- `OOMKilled`
- неправильные environment variables
- ошибка подключения к базе данных
- неправильные readiness/liveness probes
- ошибка в startup-логике приложения.

## Возможные ложные срабатывания

- плановый rollout
- ручной restart deployment
- node drain
- изменение конфигурации с перезапуском pod'ов

---

# 8.4. Alert: Spark Job Failed

## Назначение

Алерт срабатывает, если хотя бы одна Spark-job завершилась с ошибкой.

## Пояснение

Batch-job обычно запускается не постоянно, поэтому падение даже одного запуска может быть важным. Например, если ночная обработка статей не прошла, пользователи утром увидят старые данные.

## Severity

`critical`

## Возможные причины

- некорректные входные данные
- ошибка чтения из S3
- ошибка записи результата
- нехватка памяти executor'ам
- data skew
- проблема с зависимостями
- ошибка в коде Spark job.

## Возможные ложные срабатывания

- job была отменена вручную
- тестовый запуск
- backfill на заведомо грязных данных
- временная недоступность хранилища.

---

# 8.5. Alert: Spark Job Has No Recent Success

## Назначение

Алерт срабатывает, если регулярная Spark-job давно не завершалась успешно.

## Пояснение

Если job должна успешно выполняться раз в сутки, то отсутствие успешного запуска больше 26 часов означает проблему. Взято 26 часов, а не ровно 24, чтобы оставить небольшой запас на задержки расписания и увеличение времени выполнения.

## Severity

`critical`

## Возможные причины

- scheduler не запустил job
- job зависла
- job постоянно падает
- изменилось расписание
- проблема с доступом к данным.

## Возможные ложные срабатывания

- job временно отключили
- был maintenance window
- изменилось расписание запуска
- job больше не нужна, но алерт не удалили.

---

# 8.6. Alert: Low Article Processing Success Rate

## Назначение

Алерт срабатывает, если доля успешно обработанных статей становится ниже 95%.

## Пояснение

Система может быть технически доступна, но бизнес-процесс может работать плохо. Например, статьи загружаются, но часто не проходят обработку.

## Severity

`warning`

## Возможные причины

- большое количество невалидных файлов
- ошибка в processing-service
- проблемы в Spark job
- недоступность S3
- ошибка в схеме данных
- проблема с Kafka consumer'ом.

## Возможные ложные срабатывания

- мало статей за период
- тестовые загрузки
- массовая загрузка некорректных файлов
- изменение правил валидации.

## 9. Сбор метрик с короткоживущих Spark-job'ов

### 9.1. Проблема

Prometheus хорошо подходит для долгоживущих сервисов, потому что он периодически приходит к ним на `/metrics`.

Но batch-job может жить очень недолго:

```text
job started -> processed data -> finished -> pod deleted
```

Если Prometheus приходит за метриками раз в 30 секунд, а job живёт 10 секунд, он может не успеть собрать данные.

Из-за этого можно потерять важную информацию:

- job запускалась или нет
- успешно завершилась или упала
- сколько времени выполнялась
- сколько записей обработала
- когда был последний успешный запуск.

---

### 9.2. Решение

Для короткоживущих Spark-job'ов используется Pushgateway.

Схема работы:

```text
1. Spark job стартует.
2. Spark job выполняет обработку.
3. В конце работы job формирует итоговые метрики.
4. Job отправляет метрики в Pushgateway.
5. Prometheus регулярно scrape'ит Pushgateway.
6. Grafana показывает результаты.
7. Alertmanager отправляет алерты, если job упала или давно не было успешного запуска.
```

---

### 9.3. Какие метрики отправлять в Pushgateway

Пример итоговых метрик:

```text
spark_job_runs_total{job_name="article-etl-job", status="success"} 1
spark_job_duration_seconds{job_name="article-etl-job", status="success"} 124
spark_job_last_success_timestamp_seconds{job_name="article-etl-job"} 1760000000
article_processing_total{pipeline="article-etl", stage="normalize", status="success"} 1500
article_processing_total{pipeline="article-etl", stage="normalize", status="failed"} 12
```

Эти метрики отвечают на главные вопросы:

- job завершилась успешно или нет
- сколько она выполнялась
- сколько записей обработала
- сколько ошибок возникло
- когда был последний успешный запуск.

---

### 9.4. Что не нужно отправлять в Pushgateway

В Pushgateway не нужно отправлять:

- CPU usage каждую секунду
- память executor'ов каждую секунду
- данные по каждому пользователю
- данные по каждой статье
- уникальные `run_id` в labels без необходимости.

Pushgateway должен хранить компактные итоговые метрики, а не превращаться в отдельную базу событий.

---

### 9.5. Дополнительная защита от потери метрик

Pushgateway решает большую часть проблемы, но есть крайний случай: Spark job может умереть до того, как успеет отправить метрики.

Поэтому дополнительно нужно мониторить Kubernetes Job status через `kube-state-metrics`.

Например, если Kubernetes показывает, что job завершилась неуспешно, а в Pushgateway нет успешной метрики, это тоже должно считаться проблемой.

Такой комбинированный подход надёжнее:

```text
Spark final metrics + Kubernetes job status
```

---

## 10. Безопасность мониторинга

### 10.1. Доступ к `/metrics`

Endpoint `/metrics` не должен быть публичным.

Рекомендуется:

- держать `/metrics` на отдельном порту
- не публиковать его через внешний Ingress
- разрешить доступ только из namespace, где находится Prometheus
- не отдавать в метриках персональные данные.

---

### 10.2. Доступ к Grafana

Grafana должна быть защищена авторизацией.

Роли:

| Роль | Права |
|---|---|
| Viewer | Просмотр дашбордов |
| Editor | Изменение дашбордов |
| Admin | Управление Grafana |

Для учебного проекта достаточно описать, что Grafana доступна только авторизованным пользователям.

---

## 11. Итоговая конфигурация по слоям

| Слой | Что мониторим | Чем собираем | Где смотрим |
|---|---|---|---|
| Kubernetes | Pod'ы, контейнеры, node'ы, рестарты | kube-state-metrics, node-exporter | Kubernetes / System Health |
| Микросервисы | RPS, error rate, latency | `/metrics` в сервисах | Microservices / API Performance |
| Spark | Запуски, duration, failed tasks, executor memory | Spark metrics, Pushgateway | Spark Batch Jobs |
| Бизнес | Загрузки, обработки, success rate, queue lag | Метрики сервисов и Spark | Business Metrics |
| Алерты | Ошибки, задержки, падения, отсутствие успешных job'ов | Prometheus rules + Alertmanager | Уведомления |

---

## 12. Заключение

В проекте предложена система мониторинга для Kubernetes-кластера, где одновременно работают долгоживущие микросервисы и Spark batch-job'ы.

В архитектуре используются:

- Prometheus для сбора и хранения метрик
- Grafana для визуализации
- Alertmanager для уведомлений
- kube-state-metrics и node-exporter для Kubernetes-инфраструктуры
- Pushgateway для короткоживущих Spark-job'ов.

В документе описаны ключевые метрики с labels, четыре Grafana-дашборда с PromQL-запросами, шесть правил алертинга с severity и возможными ложными срабатываниями. Отдельно решена проблема короткоживущих Spark-job'ов: такие задачи отправляют итоговые метрики в Pushgateway, после чего Prometheus забирает их обычным scrape-механизмом.
